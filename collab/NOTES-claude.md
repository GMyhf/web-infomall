## 2026-08-07 · T-013 任务书（交给 Codex）：把概率兜底换成确定性覆盖

人指派 T-013 给你。下面是我替你做完的侦察，以及我希望你**别顺着我框架走**的地方。

### 靶子

`find_first`（`common.h:288`）——整条查询路径的核心，`get_page` / `get_versions` /
前缀搜索三处都走它。九行代码：

```cpp
int lo = 0, hi = static_cast<int>(count);
while (lo < hi) {
    int mid = (lo + hi) / 2;
    if (entries[mid].url_hash < hash) lo = mid + 1;
    else hi = mid;
}
return (lo < (int)count && entries[lo].url_hash == hash) ? &entries[lo] : nullptr;
```

### 我侦察到的四条事实（省你时间，请自己复核）

1. **手搭夹具最大只有 2 条 entry。** `test_core.cpp` 里 `make_host_block` 全部 6 处调用，
   `entry_count` 分别是 2 / 1 / 1 / 1 / 2 / 1。**二分查找从没真正递归过。**
2. **两条变异对现有 495 项完全不可见**：`hi = mid - 1`、`while (lo + 1 < hi)`。
   我实测过，`test_core` 全绿。**只有 `bench` 的随机抽样能抓到**（126/500、136/500）。
3. **随机抽样是概率兜底，不是覆盖。** T-012 让闸门有了兜底，但换个抽样规模就可能漏——
   我在 T-011 里就撞见过一次：`lo = 1` 那条变异在深归档上 **0 misses**，
   纯粹因为随机抽样没抽中第 0 条。**这条任务的意义就是把那份运气去掉。**
4. **`get_versions` 只在一处覆盖到 2 个版本**（`test_core.cpp:732`，走真实 indexer 的
   roundtrip 测试）。

### 为什么「同 URL 多版本」是这条任务的另一半

这个函数叫 `find_first` 而不是 `find`，是有原因的：**同一个 URL 的多次抓取，
`url_hash` 完全相同**，它们在 block 里连成一段（按 `crawl_date DESC` 排）。
`find_first` 必须返回这一段的**第一条**，调用方才能用
`while (block[idx].url_hash == hash)` 往后扫完整段。

**返回段中间的任何一条，`get_page` 仍然可能"看起来对"**（它扫到的那部分里若含目标 URL 就返回了），
但 `get_versions` 会少算版本——而"某个 URL 有几个历史版本"正是这个项目的核心功能。

所以这一半的判据是：**造一个 URL 有 K 个版本（K 足够大，比如 20+）的 block，
断言 `get_versions` 返回 K 条、日期齐全且有序**。
构造上很简单——同 URL 不同 `crawl_date`，`url_hash` 自然相同，你不需要伪造哈希。

### 建议的判据（这是我的框架，不是要求）

- **确定性**：造一个 N 条 entry 的 block（N 取几百量级即可，`test_core` 现在 0.9 秒，别撑爆它），
  **对每一条**断言 `get_page(url).url == url`。不抽样，全查。
- **边界**：第 0 条、第 N-1 条、以及不在 block 里的 URL（必须返回未找到而不是相邻条目）。
- **多版本**：如上，K 个版本全部取回。
- **硬要求**：每条新断言做变异自检，**并先 `diff -q` 确认变异真的生效**
  （见 `collab/README.md` 硬约束第二条——那条是我上一轮踩出来的）。
  至少要能抓住 `hi = mid - 1` 和 `while (lo + 1 < hi)` 这两条。

### 你会遇到的实际工作量在哪

不在断言，在**构造**。`write_v2_shard` 要求 entry 按 `url_hash` 排序、
`url_offset` 指向 url_pool 里对应的切片。造 N 条就得：生成 N 个 URL → 算 hash → 按 hash 排序
→ **按排序后的顺序**拼 pool 并回填每条的 `url_offset`。
现有 `make_v2_entry` 不替你做这件事（它只接受你算好的 offset），
`test_v2_shard_validation_and_legacy_dates` 里那段 `if (ordered_entries[1].url_hash < ...) swap`
就是这个问题在 N=2 时的手工版。**建议把这段抽成一个 helper**——T-006 的红队夹具和
将来任何深 block 测试都会用到它。

### 我想被质疑的地方

- **N 取几百是我拍的。** 我的依据只是「`test_core` 现在 0.9 秒，别让它变慢太多」。
  如果你算出更小的 N 就足以让二分递归到足够深度（log2(N) 层），用更小的，并说明理由。
- **我可能又把靶子选窄了。** 我盯着 `find_first`，是因为我有它逃逸的实测证据。
  但 `find_host_range`（`query.cpp`，host 层二分）同样是二分查找，
  同样只被小夹具覆盖过——如果你认为它更值得先补，推翻我。
- **T-011 的教训请你也带着**：我上轮"更深 = 覆盖更多"的直觉是错的。
  造大 block 之前，先想清楚**它到底让哪一条判据从概率变成确定**，
  别造一个大而无用的夹具。

我本来想用 `bench` 当深 block 的正确性断言，翻开一看 `bench.cpp:105` 是 `(void)result;`——

## 2026-08-07 · 复核 `3c38594`（T-006）：认可。顺手量了一次闸门，量出个比 T-006 大的东西

### 一、T-006 认可，那条 magic 注释是真发现

「翻转 v2 magic 的最低位会变成受支持的 v1 magic（`IDX!` → `IDX `）」——
这是自己动手做变异才会撞见的东西，读代码读不出来。而且你**发现后改用了另一个单比特变异**，

`test_core` 只要 **0.9 秒**，476 项一点不贵——我原本担心「每个前缀都截断」会让计数虚胖、
拖慢闸门，实测两个担心都不成立。

### 二、我补强的：复位断言只查了八分之三，而且循环根本钉不住它

`fail()` 复位 **8 个**字段，原断言只查 `fd`/`data`/`header` **3 个**。
漏掉的 `hosts`/`entries`/`url_pool` 恰恰是**指向已经 munmap 掉那块映射的指针**——
失败的 open 若漏掉它们，忽略返回值的调用方就会解引用已释放的页。这正是红队该抓的那类。

但更要紧的是第二层，我是被变异逼出来才看清的：**截断循环钉不住这三个字段。**
我把 `url_pool = nullptr` 删掉，测试**照样全绿**——因为绝大多数截断前缀在这些字段
被赋值之前就失败了，它们本来就还是 nullptr。

**所以复位断言必须加在「后期失败」的用例上**（排序错、offset 越界、尾随字节——
那些走完布局校验、指针已经赋值才失败的）。已加，四个字段逐一变异，全红。

### 三、方法上的一条，我这轮自己踩了

我第一遍跑这两条变异时，结论是「都没被抓住」。查下来是**我的正则没匹配上，变异压根没生效**。

**一个没生效的变异，和一个抓不住的变异，输出长得一模一样。**

这和我们这几轮反复撞见的是同一类错误——证据在传递途中被悄悄丢掉，
而调用方拿到一个看起来正常的结果（review 包只剩文件名、跳过的步骤无声消失、
成功只打一个 ✅）。我现在的变异脚本一律先 `diff -q` 确认文件真的变了，
没变就打 `⚠️ 变异未生效，结果无意义`，绝不让它冒充「未被抓住」。

### 四、真正的发现：`load` 一次 45 秒，2178 次 fsync

顺手给闸门计了个时：`make -C src test` **6 分 7 秒**，但只有 18s user + 49s sys——
**五分钟在等，不在算**。逐套拆开：

| 套件 | 耗时 |
| --- | --- |
| `test_parse` | 0.1s |
| `test_core`（T-006 的 476 项） | **0.9s** |
| `test_load_checkpoint.sh` | 126s |
| `test_http_server.py` | 60s |
| `test_archive_tools.py` | 166s |

再拆：单次 `load` **45 秒**，而 `verify` 和 `bench` 各 **0.1 秒**。
`strace -c` 给出原因：**2178 次 fsync，占系统调用时间 99.4%**。

机制在 `store.cpp:94-101`：`DataStore` 只保持一个打开的数据文件，
**文章月份一变就 `close_current()`——fflush + fsync(文件) + fclose + fsync(目录)**。
而 `.dat` 里文章日期是乱序的，样例 1000 篇跨 **111 个月份目录**，
于是几乎每条记录都触发一次换月。2178 ≈ 2 × 1089 次切换，数字逐项对上。

**这不只是闸门慢。** 本项目的立项目标就是加载 1400 万篇——
如果全量数据同样乱序，**这个代价不是常数，是按记录数增长的**。
没人跑过全量加载，所以它一直没暴露。

已开 T-010，**标了待人拍板**，并在任务里写死一句：
**不要用「少 fsync 几次」来修。** 红线 1 与 CP3 要求的是
「数据与全部索引落盘后才把源从 tainted 提升为 completed」——
那是**一次加载结束时**的契约，不是每次文件切换的契约。
按月保持多个句柄（带上限）、`finish()` 时统一 fsync，契约不变而 fsync 从 2178 降到约 222。
但这是耐久性/崩溃窗口的取舍，不该由 agent 定。

顺手把 `test_archive_tools.py` 的 3 次 `load` 压成 1 次（拷贝干净归档做故障注入），
**166s → 67s**，三条变异复跑全部仍变红。这一处纯属测试内部，不碰生产代码。

### 一、拆分本身认可

三条诊断各说各的，`offset` 检查前移到 payload 之前——**这个顺序是对的**，

### 二、我改的那处：一个词和它的全部行为对不上

新加的记录侧日期分支写的是 `WARNING:`，但它 `structural_errors++`、`break` 掉整个
数据文件的扫描、并让退出码变成 1。**实测输出里它就明明白白计在 `Structural errors: 1` 下面。**

这不是措辞洁癖。这个文件有一套一致的两级体系，我把每个分支都数了一遍：

| 层级 | 出现在 | 计数器 | 控制流 |
| --- | --- | --- | --- |
| `ERROR:` | `scan_data_file` 的全部 7 个分支 | `structural_errors` | `break`（放弃该文件） |
| `WARNING:` | 索引条目侧 3 处 | `bad_entry_refs` | `continue`（继续扫） |

**新加的那行是唯一的例外**：说 WARNING，走 ERROR 的计数器和控制流，

我按**你自己注释里的判断**改成了 `ERROR:`（「Legacy index dates are still serviceable;

### 一、T-005 的核心是一个方向问题，不是一个配置项

`--trusted-proxy-hops N` 听起来是加个开关，真正的内容只有一句：
**从链条右端数，不是左端。**

`X-Forwarded-For` 的直觉读法是「客户端排第一」，于是取最左那条。
**那正好是攻击者唯一能完全控制的条目**——客户端自己写的 XFF 会被代理原样保留，
代理只在右边追加它看到的地址。取最左 = 把限流键交给攻击者，
而且这个错误在正常流量下**完全看不出来**：有代理时最左通常就是真客户端。

所以我把它写成了测试里最硬的一条：31 个请求，XFF 都是 `伪造前缀, 10.0.2.7`。
取右端 → 全部落进同一个桶 → 必然 429；取最左 → 每个请求各自一个桶 → 一个 429 都没有。
**这条断言存在的唯一目的就是钉死方向。**

### 二、变异自检 4 条，第 3 条没被抓住——查下来是等价变异

按我给 Codex 定的硬要求，我自己也做了。结果：

| 变异 | 结果 |
| --- | --- |
| 取最左条目 | ✅ 变红 |
| 永远用 peer（等于功能没实现） | ✅ 变红 |
| `hops=0` 也照读 XFF | ❌ **没变红** |
| 去掉跳数范围校验 | ✅ 变红 |

第 3 条查明是**等价变异**：`hops=0` 时 `remaining` 为 0，`--remaining` 无符号回绕成
`SIZE_MAX`，循环永远取不到条目，最后照样落回 peer。行为真的相同，
**所以没有任何测试能区分它**——等价变异不是测试漏洞，追它是浪费。

但它暴露了另一件事，而且我认为这才是这轮最值钱的发现：
**那个 `hops == 0` 的 guard 今天成立，靠的是无符号下溢这种巧合。**

现在等价性是设计出来的，不是撞上的。

### 一、红线清单的来源，以及它可能错在哪

`collab/README.md` 那 10 条红线，我是从 `CHANGELOG.md`（尤其 `29d7469` 那次加固）、
`README.md` 和源码里**倒推**出来的，不是谁交给我的既有约定。倒推有个固有的失真：
**我看到的是「当前实现是这样」，我写下的是「这一条不许动」**——这两者之间隔着一次
我没有依据的升格。

最可能被我升错的两处：

- **红线 2（checkpoint 的 tainted→completed 语义、被中断的源不自动重放）**：
  CHANGELOG 把它描述成一个有意的设计（重放=重复追加=静默污染），我据此写成红线。
  但「不自动重放」的代价是「中断后只能重建整个归档」，对 1400 万篇的全量导入来说
  这个代价相当大。如果 `load.cpp` 里其实留了更细的恢复路径而我没读到，这条应当改写。
- **红线 5（DoS 面的具体阈值：队列 256、30s 超时、30 次/5 秒）**：我把**具体数值**
  写进了红线。数值是可调的工程参数，不是安全边界；真正的红线应该是「这些机制存在」
  而不是「这些数字不变」。我倾向于保留现在的措辞（改数值时至少要被人看见一次），
  但如果你觉得这会在正常调参时制造无谓摩擦，改掉它。

### 二、我对 `99d97d3` 的看法（PLAN T-002）

最近一次提交把 `MappedShard::open` 里对 `valid_crawl_date` 的拒绝删掉了，
理由写在注释里：历史快照含 `20030229` 这类历法非法值，在这里拒绝会让结构上完全安全的
索引无法服务。**这个理由我认可**，而且注释声称「integrity verification reports these
values separately」——我去核了，属实，`src/verify.cpp:423` 确实单独报。

我不放心的是另一件事：**这是一处放宽，而放宽之后没有任何测试站在那个位置。**
现在既没有「含 20030229 的 shard 能被正常服务」的正向用例，也没有「日期字段之外的
结构性损坏仍然被拒绝」的反向用例。也就是说，将来任何人（包括我）在这一段继续往下删，
闸门不会红。放宽本身合理，无人看守不合理。

写 T-002 时我特意没有把它写成「这个提交有问题」——它没问题。问题是它留下的空位。

### 三、闸门工具本身的三个坑，都是跑出来的不是想出来的

我写完 `tools/handoff.py` 后真跑了一遍，三处当场炸/漏。记下来是因为**它们都是
「移植一份看起来能用的脚本」时不会想到、只有真跑才会暴露**的：

1. **闸门自己崩在 `UnicodeDecodeError` 上。** `test_parse` 打印归档正文预览时按**字节**
   截断，收尾常是半个 UTF-8 字符（你在 `make test` 输出里能看到那些 `�`）。
   `subprocess.run(text=True)` 默认严格解码，直接抛异常——**被测代码完全没问题，
   是闸门自己红的**。这在一个专门处理 GB18030↔UTF-8 的项目里格外讽刺。已加 `errors="replace"`。
2. **尾部不是「最后发生的事」。** 原来分别抓 stdout / stderr 再拼接，等于按**流**排序而不是
   按时间排序：`make test` 的 `Leaving directory` 会排在 test_core 的错误行前面。
   而尾部正是交接记录里唯一被引用的部分——排错了就等于引错了。改成 `stderr=STDOUT` 合流。
3. **未跟踪的新文件在 review 包里只有文件名、没有内容。** `git diff HEAD` 不含未跟踪文件，
   所以本轮这种「几乎全是新文件」的交接，审查方打开包会看到一份空改动。
   已改成对每个未跟踪文件跑 `git diff --no-index /dev/null <file>` 生成正规 hunk。
   这里还踩了第二层：`--no-index` **有差异时退出码就是 1**，而原来的 `git(soft=True)`
   在非零退出码时返回空串——**把要的东西连同"错误"一起丢了**。单独加了 `git_out()` 忽略退出码。
   附带的防线：单个未跟踪文件超过 100KB 或不是 UTF-8 文本就跳过，
   免得哪天有人在工作区里留了个归档产物，整个 review 包被灌爆。

第 3 条对本项目尤其要紧：`.gitignore` 里躺着 `data/` `index/` `archive/`，
未跟踪文件里出现 GB 级二进制是**正常状态**，不是意外。

我还做了一次变异自检：把一个语法错误文件塞进 `py_compile` 那步，确认闸门确实变红
（`ok=False`、输出里有 `❌ exit`）。一个从来没红过的闸门不能证明自己会红。

### 四、我对源脚手架做的唯一一处改动，以及为什么

源版本 `run_verify` 在步骤成功时只往 review 包里写 `✅ ok`。但同一个仓库的 README
写着「交回时必须附一次真正跑完的验证结果（`--verify` 输出必须包含全套测试尾部计数）」。
**规则写下来了，工具却把证据丢了**——成功路径上一个 `✅` 和一个「我觉得没问题」
在信息量上是等价的。本版成功时保留每步尾部 12 行（`TAIL_LINES`），
所以 `PASS: 89 core checks` 这类数字会真的进到交接记录里。

如果你觉得 12 行太吵，调 `TAIL_LINES`；但请不要退回到只打印 `✅`。

### 五、还没做、我也不打算替人做的两件事

`PLAN.md` 里 T-004（Python 原型去留）和 T-005（反代后的限流口径）都标了**待人拍板**。
T-005 尤其不该由 agent 决定：信任 `X-Forwarded-For` 意味着任何人伪造一个头就能绕过限流，
这是安全边界的移动，不是实现细节。我只把现状核清楚了写进 PLAN——
限流键是 `getpeername` 的 `sin_addr`（`src/server.cpp:1923–1926`），全仓库没有任何
`X-Forwarded-For` 处理，所以 `docker-compose.yml` 那种部署下「每 IP 30 次/5 秒」
事实上是「全站 30 次/5 秒」。这个事实本身值得人看一眼，不管最后怎么定。
